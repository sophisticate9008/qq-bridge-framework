# 安装、组件更新与卸载

本文描述 2.0 候选的安装更新策略。候选尚未正式发布；实际验证范围见 [验收记录](VALIDATION.md)。

## 归属与固定入口

框架、DSH、QQ 协议端分别安装、更新和卸载。框架更新器仅替换框架发行清单中的程序；配置、会话、工作区和私人扩展原位保留。下载归档带版本号，日常服务入口保持固定。

桥接组件由框架发布，但作为 DSH 的原生组合包安装，由 DSH 插件管理器管理依赖、选择状态、加载与移除。运行插件不能链接到框架部署快照、下载暂存区或框架更新备份。DSH 自己的内容寻址包存储属于其包管理器的实现，不由框架维护程序回收。

框架卸载与桥接组件移除是两个明确操作。保留桥接组件不会影响 DSH 的其他功能；希望彻底解除接入时，应先通过 DSH 移除桥接组合包，再删除框架程序。会话、配置和工具执行证据不随程序卸载自动删除。框架不会借卸载操作删除 DSH、QQ 客户端或它们的数据。

## 组件发行与下载

框架、SDK、桥接组件保持同批版本。桥接包包含 DSH 原生组合包清单和加载 patch，用户无需手写 Loader 装配。组件从固定官方 Release 下载，并按同版 SHA256SUMS 核验；离线安装使用同一归档。发布记录保留历次版本与校验文件。

下载、安装、启用、运行中版本和协议兼容分别展示。下载成功不表示安装完成，安装成功不表示热重载成功，服务能连接也不表示实际模型和工具已验证。DSH 报告需要重启时保留该状态，由其自己的生命周期管理入口处理。

安装归档应保存在 DSH 管理者的持久包目录中，以便重新安装和回滚；不能把临时下载文件作为长期依赖来源。目录名称可以记录归档版本，DSH 加载始终通过固定包名解析。

## 更新与故障恢复

1. 先读取框架、桥接组件、DSH SDK／协议和安装来源，核对兼容要求及现有插件选择状态。
2. 下载并核验候选归档；候选不可用时原安装继续工作。
3. 通过 DSH 原生插件管理器明确更新桥接组件，保留原归档与操作编号；框架更新独立执行。
4. 区分依赖安装、组合包选择、实际加载和已鉴权接口。变化后的加载代次要求框架重新建立自身连接，不重放消息、工具或未知发送。
5. 响应丢失先查询原操作及实际版本；不能因读不到活动安装就推定成功、失败或安全重试。
6. 回滚明确选择原版本并重新核验；有未决操作时先核对，不能重复执行卸载或安装。

DSH 原生管理器有其明确限制：未启用热重载时部分变化需要重启；启用热重载时已有同名包可能必须先移除；激活失败可能保留已保存依赖。调用方必须展示实际结果，不能把“先删后装”描述成保证原版本不受影响的原子更新。

旧手工加载行、目录链接和未知归属需要迁移检查。明确识别的框架专属行才可迁移；其他插件、原有模型与权限配置保持。迁移前保存清单、锁文件与相关加载行，异常时保留可核对证据。

## 协议分工

MCP 用于独立工具、资源和提示词服务，ACP 用于客户端与 Agent 的会话接入。通用能力优先通过适合的标准协议复用。DSH 桥接适配层处理其内部请求关联、会话事件、来源与加载代次证据；是否能迁移到标准接口，以实际能力和端到端验证为依据。

## 验收矩阵

- 干净安装、重复安装、下载中断、校验失败、版本或 SDK 不符。
- 原目录框架升级与回滚、桥接组件独立升级与回滚、框架卸载后 DSH 独立启动。
- 删除框架旧快照、下载暂存区及来源归档后，已安装插件仍可加载；重新安装使用仍可取得的持久归档。
- 插件停用、移除、DSH 重启、热重载不可用、响应丢失与未决安装核对。
- 旧链接／手工加载迁移，保留非托管插件、模型、权限、会话与未知结果。
- Linux x64／ARM64 和 Windows 使用同一发行包完成实际安装检查；Docker 保持外部 DSH 独立。
- 当前真实模型渠道在隔离 DSH 中完成实际入站、工具、助手与本地出站捕获；实际 QQ 验证单独记录。

## 管理命令与记录

```sh
qbf-cli bridge status
qbf-cli bridge download 2.0.0
qbf-cli bridge install 2.0.0
qbf-cli bridge update 2.1.0
qbf-cli bridge rollback 2.0.0
qbf-cli bridge remove
qbf-cli bridge reconcile <原操作UUID>
```

版本是命令示例，以实际已发布版本为准。`download/install/update/rollback` 可加 `--from <解压完整包>` 使用同版离线组件；回滚旧归档也须已缓存或可从官方发行取得。写操作在执行前打印编号，可用 `--operation-id <UUID v4>` 固定编号。相同编号和参数返回原记录，不能改变目标版本。记录在 `DSH_HOME/storages/qbf-bridge-management/`，跨进程互斥锁核验 PID 与启动身份；只有已证实死亡的持有者可回收。

原生安装请求未知时，reconcile 只查询原请求及实际配置、加载版本，不执行第二次安装或移除。原生管理器不保留已结束请求，读到 null 不能当作失败。目标版本、选择状态与加载证据足够时才确认；仍不确定则继续 unknown 并阻止新写操作。在 DSH 管理界面核对原操作和故障日志，恢复该操作原目标后再 reconcile；不要删除 journal 或换编号绕过。候选激活失败且残留依赖时，自动恢复旧包也可能受阻，此时保留 unknown，由 DSH 管理者处理残留再核对。

启用热重载的替换只处理来源精确对应上述持久归档的已管理包。先核验新旧两份归档，再移除同名旧包；明确失败时尝试恢复旧包，结果仍需核验。插件卸载或代次变化会中断框架连接，应在聊天与后台工作排空后执行。当前命令不承诺跨 DSH 原生管理操作的全局排空或无中断更新。

## 1.x 迁移到 2.0

1. 停止框架聊天并核对未决执行、发送与后台工作；备份框架数据及 DSH profile 的 package.json、锁文件和桥接加载配置。
2. `bridge status` 若显示 legacyInstallation，不自动修改。通过 DSH 自己的配置/插件入口停用并删除**确切属于桥接插件**的旧手工加载行；移除该包的旧 link/file 依赖与 node_modules 链接，由原包管理器更新锁文件。其他包、模型、权限与会话保持原状。框架程序不要充当 DSH 包管理器。
3. 必要时由 DSH 管理者重载引擎，确认原桥接加载行已不存在；使用 `bridge install 2.0.0` 安装原生组合包。遇到未知来源或没有可用原生管理器时停止迁移，按 DSH 官方安装流程处理，不直接覆盖配置。
4. 核对 `installedVersion`、`loadedVersion` 与协议能力，再使用新包覆盖框架原安装目录；跨主版本必须显式 `--allow-major`。保留旧框架包和原配置备份，以便回退时恢复原桥接安装方式。
5. 启动框架，核验已有会话与未知执行证据，再在授权会话验证新消息。2.0 继续读取 schema 1 配置与会话数据，不要求清空或重建会话。

一键恢复从 2.0 起仅启停 framework-admin/framework-gateway，保留原运行意图，复用已应用设置。即使服务清单显式托管 DSH 或其他辅助服务，也不将它们纳入聊天自愈。明确的 DSH 维护入口仍按独立授权、排空与归属核验执行。该恢复语义和插件安装工作流变化需要主版本迁移；既有 SDK 与线协议不人为破坏。

## 卸载

先排空框架工作，再明确执行 `qbf-cli bridge remove` 或在 DSH 中移除同名组合包。确认已卸载后可以删除框架程序；按原进程管理器注销框架服务。框架数据、DSH 会话与持久归档分别由用户决定保留；命令不删除其他依赖或运行数据。仅删除框架也不会使已安装的原生插件丢失来源。
