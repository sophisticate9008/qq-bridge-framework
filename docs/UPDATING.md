# 框架更新与兼容

升级保留已公开的配置、持久数据、SDK 和协议。启动默认目录见 [目录说明](DIRECTORIES.md)；自定义安装用 `--config` 指定实际配置。新增配置提供缺省值，新增接口使用可选能力；不通过删除会话、重置权限或重放未知执行完成升级。需要破坏已承诺接口或数据格式时，使用新的主版本、单独迁移说明与显式迁移步骤。发行版本与持久 schema 分开管理。

## WebUI 更新

完整发行包安装依赖并初始化后，使用 `npm run cli -- serve` 启动。Windows 双击启动器默认使用此监督入口。左上角“配置工作台”下方的版本按钮就近打开版本与更新悬浮窗；同主版本有新 Release 时可点击“更新框架”。下载、SHA-256 校验、组件清单校验和新依赖安装先在独立目录完成。监督进程读取本安装的 DSH 连接，准备新旧桥接归档并记录原启用状态，然后停止自己的框架子进程，更新桥接组件、核验实际加载，再备份和替换框架程序。桥接组件需要重载时调用受控本机 DSH 重启。新宿主启动后核对实际版本；保存的运行意图要求聊天运行时，还需通过聊天及助手的完整健康检查。失败时协调恢复原组件组合并核验旧宿主。

管理页面短暂断开期间保持原更新编号，按该记录核对结果；不自动重发更新请求。需要再次尝试时先读到明确失败状态。当前运行程序的版本以刷新后的侧栏版本为准。更新只管理本框架登记的内置组件。DSH 本体、QQ 协议端和其他插件保持各自的更新方式；明确托管的本机 DSH 可为加载桥接组件受控重启。没有配置 DSH 的安装只更新框架程序。已配置 DSH 但无法核验归属、原生管理权限或旧归档时，更新停止，不把未知状态当作成功。

源代码工作树使用 Git 更新，Docker 使用替换容器。普通 `start` 前台入口继续可用；没有监督进程时，网页提供版本、下载与命令说明。

## 命令行覆盖更新

先停止框架宿主和网关，备份实际运行数据，下载新完整包并核对 `SHA256SUMS`，解压到另一个目录。1.12 起可在旧安装目录执行：

```sh
npm run cli -- update /srv/qq-bridge-framework-新版本
npm run cli -- serve
```

从具备完整发行清单的旧版升级时，使用新包提供的独立入口：

```sh
node /srv/新包/dist/scripts/update-framework.js --target /srv/原安装目录
```

Windows 使用相同 Node 命令，路径含空格时加双引号。命令行更新时宿主保持停止，只核验安装文件及桥接组件的实际加载，保留运行意图；聊天和助手在下一次启动后核验。工具会安装锁定生产依赖；需要网络和写入安装目录的权限。工作目录的源与目标必须分开，不放在彼此内部。跨主版本默认拒绝，仅在完成该版本迁移准备后显式传入 `--allow-major`。

发行包 `distribution.json` 同时锁定本批 SDK、DSH 桥接归档的版本和 SHA-256，并要求组件记录与公开文件清单一致。它包含公开文件的路径、大小、SHA-256、执行位以及 `compatibility: { data: 1, overwrite: 1 }`。更新只替换该清单中的程序文件，并清理旧清单声明、而新版已移除的程序文件。2.x 整套更新要求旧安装具有可核验的完整清单。缺少文件清单的早期 1.x 安装，先使用对应 1.x 包的独立更新入口升级到 1.13.7，再按 2.0 迁移步骤处理桥接组件；不要直接套用 2.x 更新器。始终保留 `runtime/`、`data/`、`workspace/`、`private/`、自定义文件、凭据、会话和权限配置；不删除外部 DSH 与协议端的数据。不要把自己的持久数据放到发行清单覆盖的程序文件中。

自己的更新脚本也可以停止服务后将新包内容覆盖到原目录，再执行 `npm ci --omit=dev`；不使用会删除目标额外文件的镜像同步选项，不删除 `runtime/`、`data/`、`workspace/` 和 `private/`，不重新执行初始化。推荐使用内置事务更新器，以清理过期程序文件并保留回滚能力。

## 中断与回滚

整套操作记录保存在 `data/product-updates/<操作编号>.json`，预先关联桥接操作、补偿操作、程序事务和原运行意图；DSH 重启另记确认状态，丢回包后只核验加载证据，不再次执行同一重启。程序备份和写前日志保存在 `data/framework-updates/<事务编号>/`。运行数据原位保留。整套回滚恢复本次变更前的桥接选择及启用状态，再恢复程序与依赖；确认原组合后才恢复运行。更新未完成时 `.framework-update.lock` 阻止普通启动；受监督启动会先恢复中断事务。停止服务后也可运行：

```sh
npm run cli -- update --rollback <整套操作编号>
npm run cli -- update --reconcile <原整套操作编号>
```

若旧入口损坏，使用保留的新包：`node 新包/dist/scripts/update-framework.js --target 原安装目录 --rollback <事务编号>`。旧版纯程序事务编号继续支持纯程序回滚。新整套操作的 reconcile 核对原组件操作，证据明确后恢复原组合；未确认的安装、移除与重启不会重放。结果仍未知时普通启动和新更新保持阻断。只有当前整套操作可回滚，避免使用历史备份覆盖后续版本。备份与下载目录不自动当作缓存清理；确认运行稳定后由维护者按实际需要保留。源码安装通过 Git 和自身部署流程回滚。

## 接口与维护审查

本轮将发行元数据、文件清单与更新状态分成独立契约，网络请求、文件替换、监督进程和 WebUI 各自负责边界。更新接口只接收版本与操作编号，不接收脚本、路径、仓库或 URL；应用阶段串行并验证进程停止，下载准备与运行数据分开。更新与自动恢复互斥，配置应用保留已有写屏障。原有 start、配置 schema 1 与协议继续可用，新能力通过 serve、可选发行清单及新增 GET/POST 路径接入。

恢复层区分连接重试、同代次只读核验、聊天生命周期恢复、受管服务修复和程序回滚。各层都有明确停止条件，不把操作响应、进程退出或读到相同版本当作业务执行已完成。完整包受监督更新负责本框架程序及登记的内置桥接组件；多账号共享 DSH、外部 DSH／协议端升级和 Docker 宿主管理仍使用各自明确部署入口。


## 2.0 组件与迁移

框架更新继续覆盖原安装目录，下载包名称可以带版本；不要求服务路径随版本变化。日常更新统一协调桥接组件，`qbf-cli bridge` 保留为低频组件维护入口；归档、依赖与实际加载版本分别核验，整套维护期间独立组件写操作互斥。旧手工行与指向框架快照的链接需要显式迁移。2.0 的迁移、回滚、卸载与原生管理限制见 [安装生命周期](INSTALLATION_LIFECYCLE.md)。网页同主版本更新不会跨越 1.x→2.0。


## 完整卸载

先停止框架宿主、网关及监督进程，然后执行：

```sh
qbf-cli uninstall --framework
qbf-cli uninstall --framework --keep-bridge
```

默认通过 DSH 原生管理器移除本安装登记的桥接插件，再移除发行清单中的程序文件、依赖以及安装器登记的固定命令和维护 cron，注销本安装服务清单中的框架条目。DSH、QQ、其他插件、配置、会话、工作区、私人扩展和未列入发行清单的文件保留。`--keep-bridge` 保留桥接插件，DSH 无需为此次卸载可连接；登记信息、历史归档与维护记录作为保留数据不自动清理。

卸载先打印唯一操作编号，记录在 `data/product-uninstalls/`。原生移除结果未知时保留程序，不擅自开始清理。用同一 `--operation-id` 继续核对同一卸载；不能更改原 `--keep-bridge` 意图。清理中断后，可用新包的独立入口继续：`node 新包/dist/scripts/uninstall-framework.js --target 原目录 --operation-id 原编号`。程序文件被修改、命令入口被其他程序替换或存在未决整套更新时，停止清理并保留证据。源码工作树不支持程序卸载。

外部进程管理器、自行编写的启动脚本和包管理器创建的额外入口由对应安装方式管理；内置卸载只清理本安装器有精确归属记录的注册项。


当前整套桥接管理复用 Linux 本机鉴权。远程 DSH、未受管且需要重载的实例、多个账号共享的 DSH，以及旧手工加载安装均在预检或加载核验阶段说明原因；不宣称已完成自动整套更新。Windows/macOS 的桥接原生管理接入仍需相应平台验收；仅程序更新与 Docker 镜像替换各有对应安装方式。外部 DSH 界面和其他安装器不共享本框架的操作锁，维护期间应避免同时修改同名桥接包。
