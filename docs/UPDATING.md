# 框架更新与兼容

升级保留已公开的配置、持久数据、SDK 和协议。启动默认目录见 [目录说明](DIRECTORIES.md)；自定义安装用 `--config` 指定实际配置。新增配置提供缺省值，新增接口使用可选能力；不通过删除会话、重置权限或重放未知执行完成升级。需要破坏已承诺接口或数据格式时，使用新的主版本、单独迁移说明与显式迁移步骤。发行版本与持久 schema 分开管理。

## WebUI 更新

完整发行包安装依赖并初始化后，使用 `npm run cli -- serve` 启动。Windows 双击启动器默认使用此监督入口。左上角“配置工作台”下方的版本按钮就近打开版本与更新悬浮窗；同主版本有新 Release 时可点击“更新框架”。下载、SHA-256 校验、逐文件校验和新依赖安装先在独立目录完成，之后监督进程停止自己的框架子进程、备份程序、替换并重新启动。如果原聊天已就绪，还需确认新版本聊天恢复就绪；启动核验失败会回滚程序并重新启动原版本。

管理页面短暂断开期间保持原更新编号，按该记录核对结果；不自动重发更新请求。需要再次尝试时先读到明确失败状态。当前运行程序的版本以刷新后的侧栏版本为准。更新不会停止独立 DSH 或协议端；DSH 桥接组件仍由用户在 DSH 内安装配套组件，兼容性依据协议和能力核验。需要新桥接能力的版本在发行说明中注明。

源代码工作树使用 Git 更新，Docker 使用替换容器。普通 `start` 前台入口继续可用；没有监督进程时，网页提供版本、下载与命令说明。

## 命令行覆盖更新

先停止框架宿主和网关，备份实际运行数据，下载新完整包并核对 `SHA256SUMS`，解压到另一个目录。1.12 起可在旧安装目录执行：

```sh
npm run cli -- update /srv/qq-bridge-framework-新版本
npm run cli -- serve
```

从旧版（例如 1.11）升级时，使用新包提供的独立入口：

```sh
node /srv/新包/dist/scripts/update-framework.js --target /srv/原安装目录
```

Windows 使用相同 Node 命令，路径含空格时加双引号。工具会安装锁定生产依赖；需要网络和写入安装目录的权限。工作目录的源与目标必须分开，不放在彼此内部。跨主版本默认拒绝，仅在完成该版本迁移准备后显式传入 `--allow-major`。

发行包 `distribution.json` 包含公开文件的路径、大小、SHA-256、执行位以及 `compatibility: { data: 1, overwrite: 1 }`。更新只替换该清单中的程序文件，并清理旧清单声明、而新版已移除的程序文件。旧包没有清单时保留未被新版覆盖的旧文件。始终保留 `runtime/`、`data/`、`workspace/`、`private/`、自定义文件、凭据、会话和权限配置；不删除外部 DSH 与协议端的数据。不要把自己的持久数据放到发行清单覆盖的程序文件中。

自己的更新脚本也可以停止服务后将新包内容覆盖到原目录，再执行 `npm ci --omit=dev`；不使用会删除目标额外文件的镜像同步选项，不删除 `runtime/`、`data/`、`workspace/` 和 `private/`，不重新执行初始化。推荐使用内置事务更新器，以清理过期程序文件并保留回滚能力。

## 中断与回滚

程序备份和写前日志保存在 `data/framework-updates/<事务编号>/`。运行数据原位保留，回滚只还原程序与依赖。更新未完成时 `.framework-update.lock` 阻止普通启动；受监督启动会先恢复中断事务。停止服务后也可运行：

```sh
npm run cli -- update --rollback <事务编号>
```

若旧入口损坏，使用保留的新包：`node 新包/dist/scripts/update-framework.js --target 原安装目录 --rollback <事务编号>`。同一备份仅用于恢复对应更新，回滚前核对当前版本和该事务。备份与下载目录不自动当作缓存清理；确认运行稳定后由维护者按实际需要保留。源码安装通过 Git 和自身部署流程回滚。

## Docker

见 [Docker 安装](DOCKER.md)。镜像更换只改变程序层，数据卷继续挂载。容器内不安装 Docker socket，不从网页控制 Docker 守护进程。

## 接口与维护审查

本轮将发行元数据、文件清单与更新状态分成独立契约，网络请求、文件替换、监督进程和 WebUI 各自负责边界。更新接口只接收版本与操作编号，不接收脚本、路径、仓库或 URL；应用阶段串行并验证进程停止，下载准备与运行数据分开。更新与自动恢复互斥，配置应用保留已有写屏障。原有 start、配置 schema 1 与协议继续可用，新能力通过 serve、可选发行清单及新增 GET/POST 路径接入。

恢复层区分连接重试、同代次只读核验、聊天生命周期恢复、受管服务修复和程序回滚。各层都有明确停止条件，不把操作响应、进程退出或读到相同版本当作业务执行已完成。完整包受监督更新负责本框架程序；多账号批量服务修复、外部 DSH／协议端升级和 Docker 宿主管理仍使用各自明确部署入口。
