# 版本与发布规则

内置 DSH 桥接组件随框架统一交付，运行时兼容性由协议、能力与加载代次核验，不维护逐包版本允许名单。构建版本保留作诊断信息；接口契约版本与发行版本分别管理。

本批 `1.11.0 → 1.12.0` 增加有界自动恢复、版本与更新检查、完整包事务更新及 Docker 发行。已公开配置、SDK、线协议和持久数据保持兼容，按次版本统一发布三个组件。

本项目采用 [语义化版本 2.0.0](https://semver.org/lang/zh-CN/)：`主版本.次版本.补丁版本`（例如 `1.3.2`）。版本表达兼容性和交付内容，不计开发天数、提交数、修改文件数或 AI 工作轮次。

## 如何决定版本

未经用户明确要求，不提升主版本号。

| 级别 | 判断依据 | 项目例子 |
| --- | --- | --- |
| 主版本 Major | 已承诺的公共接口、配置或持久数据不再兼容，现有使用者必须改代码、改配置或迁移才能继续使用 | 删除 SDK 方法；改变同一协议字段的含义；不再读取现有配置或会话格式 |
| 次版本 Minor | 保持已有用法可用，新增可独立使用的功能、公共接口或正式弃用声明 | 新增任务与日程管理页；新增可选插件展示贡献；新增协议适配能力 |
| 补丁 Patch | 保持已有用法与功能范围，修正错误、布局、文案、性能或安全问题 | 修复删除弹窗、缓存统计、超时恢复；降低空闲 CPU；修正卡片间距 |
| 不发版 | 只有开发流程、说明或示例整理，暂时不需要交付新的安装包 | 修改贡献指南、版本规则、示例文档；日常本地提交 |

同一批发布按其中最高的必要级别递增一次。`1.3.0 → 1.3.1` 是修复；`1.3.1 → 1.4.0` 是兼容功能新增；`1.4.2 → 2.0.0` 是不兼容变更。进位时后续位归零。`1.9.0` 之后可以是 `1.10.0`，不是必须升到 `2.0.0`。

公共兼容面包括 SDK 导出、HTTP/协议接口、CLI、已公开配置及持久数据读取、权限和恢复语义。新增必填参数或要求扩展实现者补写方法也须检查是否构成破坏性变更；不能只因“增加了代码”就认定兼容。内置实现重构、需重启加载新程序、源码目录内部调整本身不意味着主版本升级。修复不应依赖的错误行为时说明影响；如实际破坏已承诺用法，仍按主版本处理。

## 发布节奏与组件版本

- 日常工作完成独立本地提交，累计到用户要求的里程碑再发布。提交、部署、推送和发布是分别授权的操作，不因提交或本机部署自动升版本。
- 正式发布与更正 Release 均先推送候选提交并跟踪远端 CI，核对完整提交 SHA，确认所有应运行任务成功后才交付。失败、取消、排队、运行中或没有检查记录均不能发布；修改候选提交后重新等待该提交的检查，不能借用旧提交或旧标签的成功结果。
- 以最近一次正式发布为基线评估整个差异，不为同一未发布批次反复升号。小改动可以合并为一次补丁发布；不设每日发版或每完成一个功能就发版的要求。
- 框架、TypeScript SDK、DSH 桥接插件采用统一发布版本。以整批变更的最高必要级别确定版本号，三个组件的包版本、安装包、描述版本和安装说明同步更新；没有业务改动的组件也随本次发布升级包版本，Release 不混放不同版本的交付包。对外线协议、服务契约及持久 schema 不因统一包版本而改变。
- 示例和私人业务扩展不决定框架版本。Release 及发布记录只描述框架、SDK 和 DSH 桥接插件的通用变化，不列本机业务插件的名称、行为或维护事项；为业务需求补齐的框架机制按通用能力描述。业务扩展的说明与维护记录独立组织。
- 服务契约版本、持久 schema、插件业务版本与包版本分别管理；不因发版机械递增。已有稳定契约不兼容时需新契约版本及兼容说明。
- GitHub Release 是永久发布档案，保留历次发布说明、安装包及校验文件；发布新版本、存储维护与本机清理均不得自动删除或修改历史 Release 及其附件。Git 标签与提交历史同时保留，不提供远端自动清理脚本或工作流。
- 仅本机发布目录采用只保留当前版本的规则：新版云端附件已上传、实际下载并通过 SHA-256 核对后，才清理本机旧版压缩包。上传或核对未完成时不清理。本机源码、Git 标签和运行数据不属于发布包清理范围。构建部署快照保留当前版本和回滚入口，旧进程退出后由存储维护回收符合条件的其余快照。
- 未稳定的新能力可在明确需要时发布 `1.4.0-rc.1` 等预发布版本，并在 GitHub 标为 prerelease。版本后缀不能代替真实验证说明。
- 默认保持已发布 tag 和安装包不变，后续修复用新版本。仅纠正文字可编辑 Release 说明。用户明确要求更正本次发布时，可同步修正该 Release 的源码标签、安装包与校验文件；先保存旧标签与附件信息，核对远端旧引用后再更新，并注明更正内容，不能留下源码与附件版本不一致的状态。

## AI 发版执行顺序

1. 阅读本规则，确认用户本轮授权的提交、推送、发布范围。读取最近正式 Release、tag 和各组件版本，对照全部待发布变更。
2. 给出简短判断：基线 → 目标版本、Major/Minor/Patch 理由、三个组件统一版本、兼容性和升级要求。无法证明兼容时先调查，不能为了降低版本而省略破坏性影响。
3. 同步三个组件的 `package.json`、锁文件根包版本、README、安装命令与发布说明，同时更新桥接插件描述版本、框架版本识别和对应夹具；兼容范围以该次发布的明确约定为准。
4. 在 GitHub 托管 CI 的干净且已提交工作树构建框架、SDK 与 DSH 桥接插件，执行 `npm run release:pack` 生成完整框架包、两个组件包及 SHA-256。完整包包含已构建后端、WebUI、字体、启动入口、公开源码及配套组件；只取 Git 跟踪的公开源文件与明确的构建目录，排除运行数据、私人文件、凭据与依赖目录。执行 `npm run test:release` 在全新目录安装锁定生产依赖，删除原 TS 源目录后验证编译后端、全部网页脚本与样式、初始化、状态、原生排版与重启。本机只做必要的定向验证、实际接入和部署核对，不重复这套完整发行安装。
5. 使用中文按逻辑提交。获授权后先推送候选分支，记录完整提交 SHA，通过 `gh run list --commit <完整SHA>` 与对应运行详情跟踪 CI；所有应运行任务成功后再创建或更新 tag，标签指向同一已验证提交。标签推送触发的检查也须确认成功。失败时先修复并推送新候选，不提前发布。
6. CI 全部通过后才创建或更正 Release，上传安装包与校验文件；说明变化、依赖、兼容组合、验证范围及限制，并附对应提交的 CI 运行链接。核对远端 tag、Release、附件版本与下载后的 SHA-256 一致后收尾；不向 npm 发布除非另有明确授权。

从 v1.7.2 开始，版本标签同时触发“发行包安装验证”工作流。该工作流在干净环境构建、打包并实际安装启动，成功后保存 `release-packages` artifact。发布使用该次 CI 已验证的附件，连同普通框架验证全部成功后才创建 Release；不为旧 Release 回填完整框架包。

从 v1.8.0 开始，版本标签的发行验证自动将同批 `release-packages` 交给 Windows x64 和 Linux ARM64，Windows 执行 ZIP、启动器、ACL 与模拟聊天链路。框架 TAR 在构建任务内由 Linux x64 验收；三个平台全部通过后才发布，Windows ZIP 与 TAR、两个组件包及 SHA-256 一起作为正式附件。

开发期 Windows 候选包由手动工作流 `windows.yml` 构建并在原生 Windows x64、Linux x64／ARM64 安装验收，产物仅作为 CI artifact 保存，不自动发布或修改 Release；使用范围见 [Windows 说明](WINDOWS.md)。完整包打包入口同时生成 Windows ZIP 与对应 SHA-256，下一次正式发布须使用该提交的全平台验收结果。

“发行包跨平台验证”是手动诊断工作流，使用 `gh workflow run platforms.yml --ref main -f release_tag=v1.8.0` 启动。它在标准 Ubuntu x64、Ubuntu ARM64 与 Windows x64 runner 上下载同一正式全量包，核对 SHA-256 与原标签提交，再安装生产依赖、验证原生中文排版、初始化、WebUI 和重启。所选发行版本须与运行工作流的源码版本相同；三个任务独立报告，失败不取消其余平台，不重打包、不改历史 Release、不部署本机。只上传三天保留的小型阶段报告和日志，不上传依赖或安装目录。新增诊断任务不自动表示对应平台已获支持，实际结果记录在验收文档。仅复核 Windows 时追加 `-f windows_only=true`，避免重复已经通过的 Linux 安装。

## 1.12 起的兼容承诺

同一主版本内的正式升级必须读取旧配置与数据，保留私人扩展及用户文件。公开接口的删除、必填参数增加、数据格式不再可读、权限或未知恢复语义改变均需新的主版本与迁移方案；维护者本次允许的大范围重构不延续为后续随意破坏兼容的许可。发行包以版本化文件清单声明程序归属，覆盖安装不得删除运行数据；CI 使用真实上一版发行包验证升级路径。详见 [更新流程](UPDATING.md)。
