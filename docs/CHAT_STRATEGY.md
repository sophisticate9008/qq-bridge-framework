# 聊天策略维护

本文是框架通用聊天策略的持续维护入口，说明当前默认值、消息进入模型的条件，以及配置和恢复边界。具体行为以链接的源码、公共契约和验证为准；人设表达、模型选择与业务扩展各自配置。日常操作见 [使用教程](USAGE.md)，会话任务见 [会话任务与续聊](CONVERSATION_TASKS.md)。

## 唤醒与续聊

白名单控制会话是否允许进入聊天，唤醒策略决定何时进入参与判断。私聊持续可参与；群聊按以下来源处理：

| 来源 | 当前规则 |
| --- | --- |
| 直接呼叫 `direct` | 真实 @ 机器人，包括只有 @ 和空白的消息；协议确认的戳一戳也能唤醒，普通文字模仿戳一戳不算。 |
| 昵称 `nickname` | 命中当前人设名称或已配置的呼叫昵称。 |
| 引用 `reply` | 开启引用唤醒且引用对象确认为机器人消息；不根据相邻发言猜测引用作者。 |
| 概率 `probability` | 白名单群聊尚未唤醒、没有排队或处理中的请求时，默认每条消息以 **1%** 概率进入正常唤醒流程。范围 0–100%，支持小数，0% 关闭；私聊不抽取。 |
| 续聊 `continuation` | 最近一次有效唤醒后的基础窗口默认 **90 秒**，期间所有发言者的消息可进入参与判断。 |

再次有效呼叫会刷新基础窗口，普通发言不刷新。每轮通过新消息覆盖检查并决定发言后，按执行编号追加一次，默认 **500 毫秒**；分气泡不重复追加，静默和被覆盖的旧结果不追加。剩余窗口随真实时间减少，最多 300 秒；基础时长为 0 关闭续聊，追加为 0 关闭动态追加。重启不从历史回复恢复临时激活窗口。

明确呼叫保留处理，但已答复、本人取消或明确要求不回复时可以保持安静。续聊、概率唤醒与普通群聊观察由模型结合语境选择性参与；他人互聊、引用他人、图片出现或还有续聊时间，都不单独构成必须答复的请求。

## 普通未读与时间事实

普通未读自动补读默认保留 **15 分钟**。在“概览 → 续聊策略”或“人设 → 唤醒与续聊”编辑“未读保留时长”，范围 **1–1440 分钟**，保存后用于后续输入。配置字段为可选的 `wake.unreadRetentionMs`，旧配置缺省采用 900000 毫秒，无需重置或回写迁移。

每轮组装输入时逐条过滤普通未读：时间有效、不晚于本轮宿主时间，且年龄不超过保留时长才自动补入；恰好位于边界的消息保留。未知、无效或未来时间不猜测为刚发生。当前输入、已受理的排队请求及补充、延期后保留的未送达请求有各自的来源，不因普通背景时限到期而丢失。纯 @ 或戳一戳没有有效未读或待答请求时作为当前招呼处理，不重新追答旧闲聊。

背景按原顺序提供最新最多 32 条，当前消息另附；默认每条正文最多 800 字符、背景字符预算 12000，仍受整体 60 KiB 和八个内容块限制。明确请求在有界预算内优先，裁剪标明 `historyTruncated`／`unread.partial`。历史、连续模型上下文、记忆、资源与绑定按各自规则保留；自动补读过期不等于删除这些数据。

输入携带当前时刻、宿主时区、消息与引用时间、上次模型确认受理时间和间隔。读取游标与受理时间只在模型请求明确 accepted 后更新；拒绝、未知结果、被动收信和重复游标不刷新受理时间。游标前进可以包含本轮明确跳过的过期背景，不代表每条历史都送给模型看过。

## 引用因超时未读而跳过的消息

普通引用只恢复指定目标。**仅当引用目标曾因未读超时而未送入模型，或本轮仍未读且确因年龄超过保留时长被过滤时，才补充目标周围的本地上下文。** 已实际提供给模型的消息、正常新引用，以及仅因时间未知而未补读的消息，不因此展开邻接。

历史保存有界的 `expiredUnreadIds` 证据，原生聊天最多随当前保留的 100 条历史保存对应 ID。只有本轮请求 accepted 后，才记录因时长过滤且未实际装入输入的消息；目标后来通过引用或其他输入真正装入并 accepted 后清除证据。记录不因准备输入或失败提交而冒进，消息被历史裁剪时对应证据也移除。

引用选择先保留当前消息的目标，再按排队来源补齐，最多四个去重目标，呈现保留来源顺序。符合超时未读条件的目标及邻接，**整轮合计最多 16 条，包含目标本身**；单目标优先前八条、后七条，一侧不足时由另一侧补齐。多目标先保留目标，再共享余下预算，重叠消息去重。

邻接只来自同一会话实际保留的历史，保留真实账号、原时间与顺序，不用最新无关消息凑数。目标已不在本地历史时，同会话协议读取只能恢复目标本身，不能推测其周围消息；缺失或截断标明 `partial`。这批内容通过 `quoteContext` 标明仅用于理解引用，不成为一批新待答请求，也不重放旧工具或旧回复。媒体句柄出现仍不代表已经读取媒体内容。

## 忙碌合并、延期与身份

群聊忙碌期间，已准入消息进入有界待发区；模型可接纳下一轮时，合成一批提交，保留各原请求的正文、真实发言者和时间。原生待发区每会话最多 16 条、合计最多 256 条，容量压力下优先合并普通观察与续聊；它不是无限消息档案。滚动历史裁剪后，保留中的队列原文仍可作为受信来源补回，读取边界沿用原历史序列，不把后来到达的消息计入旧请求已读范围。

群聊等待前一轮不消耗新批次的单轮期限；进入实际分派／提交流程时开始默认 **120 秒**的总期限，输入准备与执行共同使用该期限，进度事件不延长它。私聊保留原准入期限；具体超时策略来自执行配置。超时与外部执行是否终止分别记录，结果未知不当作成功，也不自动重放。

发送前发现新消息时，普通观察批次可延期合并一次；明确呼叫按原呼叫者的追加和纠正判断，旁人闲聊不阻止该请求完成。延期保存有界原始请求快照，通过 `replyDelivery` 告知下一轮哪些请求尚未答复；下一轮携带保留请求后，不再因持续新消息反复延期。原文最多 32 条、单条保存最多 800 字符，输入展示单条最多 400 字符、总预算 12 KiB，裁剪标明不足。

提交所用的最新发言者不会取代旧请求的实际作者。取消和纠正按各请求本人的真实表达理解，旁人换话题或发图不自动撤销原请求；需要受控工作变更时仍由工具权限核验。账号、会话、请求 ID、sessionId 与 generation 共同约束执行与资源范围。昵称、引用、转发、模型草稿或网页管理员身份不授予 QQ 主人权限。

## 发送与媒体

普通 QQ 轮次只有发送工具实际发出的内容才对用户可见：文字、引用及结构化回复使用 `qbf_reply`，收藏表情使用 `qbf_sticker_send`。模型最终正文不是普通聊天的自动发送出口。已发送回复不重复回答；历史模型输出、尚未送达的草稿和真实群聊发言分别理解，未送达草稿中编出的称呼、事实或约定不能当作共同经历。

Markdown 图片提交后先持久排队，模型收到 `queued` 即结束本轮，后台独立渲染并发送，主会话继续处理后续消息。已受理任务不因原轮或工具超时、普通新消息而丢弃；聊天停机后保留，恢复时接续尚未发送的工作。后台继续核验原绑定、当前白名单及发送权限，实际渲染资源不足、换绑、权限撤销和未知发送分别留证；未知回执不自动重发。排队、渲染完成与确认送达分别呈现，具体容量与恢复语义见 [图片排版](MARKDOWN.md)。

发送与其他副作用依真实回执区分 confirmed、rejected、unknown；unknown 先核对原操作，不重复提交。已执行工具不会因为合并、延期或恢复而重放。白名单与当前授权在入站和实际副作用前重新核验，敏感操作仍只认真实配置主人。模型提问在所属 QQ 会话答复，控制台提供配置、统计与维护。

媒体登记、取得字节、模型实际收到内容与理解内容分别记录。图片占位符或有效 `assetId` 只表明资源来源；只有模型已登记图片能力、应用配置生效且实际收到图片内容，才具备看图条件。“仅文字／文字＋图片”的登记不会代替实际模型能力。普通观察不因别人发图而自动逐张分析；需要时通过当前会话的媒体工具读取。

转发需实际展开后才能读取节点，转发作者不当作当前真实发言者。语音需要可用转写服务；视频与动图只提供所选方案的有限画面，未处理音轨时不声称听过。协议或模型能力不可用时准确说明缺失条件，不把占位符猜成内容。见 [使用教程](USAGE.md)、[视频](VIDEO.md)与 [GIF](GIF.md)。

## 保存、应用与恢复

人设唤醒、概率、续聊和未读保留设置保存后即时用于后续输入，不重置模型会话。模型服务、模型能力、聊天方案与部署配置区分已保存和实际运行版本；需要应用的变化通过页面“应用”或“应用并启动”接入，保存本身不表示运行模型已使用新设置。页面说明见 [控制台](UI.md)。

模型能力中的“最大输出”随当前供应商与模型应用到 DSH；自动准备、统一恢复和本地模拟均使用该能力值，不沿用旧部署的较小预算。最大输出只限制请求可生成的上限，思考模型可能将推理与正文共同计入；提高上限不延长单轮总期限。输出上限必须小于所配置的聊天上下文窗口，容量不兼容时在应用前提示调整，保留当前会话与运行证据。

“一键恢复聊天”由独立持久操作恢复受管本机 DSH、框架和明确受管依赖，应用已保存设置并启动聊天。协议端与独立 QQ 客户端不在启停范围。只有真实运行状态为 running、chatReady 且健康检查通过，才显示恢复完成；断线后继续核对同一操作，未知回执不重复发起。旧配置控制记录有备份，业务未知执行、发送证据与会话不清空、不重放。

当前统一恢复限可信本机 Linux 单账号部署，多账号与远程 DSH 不默认为可接管；管理 API 完全离线时无法从页面受理新操作。已受理操作由独立进程继续，停服前确认守护就绪，异常退出时有限尝试恢复受管服务与管理页面，不假报聊天完成。具体恢复边界见 [恢复手册](RECOVERY.md)。
